### 2. Three Critical Legal Boundaries Specific to UTSS

Because UTSS introspects third-party code, compiles databases, and emits source code, explicitly define these three boundaries in a root `LICENSE-POLICY.md` or `NOTICE` file:

#### A. Generated Artifacts (`.db` Catalogs & Emitted `.g.cs` Invokers)

* **The Rule:** Your repository's software license governs **the generator tools**, **not the output** they produce.
* **Why It Matters:** When a user runs `utss_csharp_bindgen.py` in their workspace to generate `UtssPackages.g.cs` or `.utss/workspace_catalog.db`, they must own 100% of those generated files under whatever license their own project uses (proprietary or open-source). Include an explicit **Generated Code Exception** in your root `LICENSE` header:


> *"Output generated by UTSS tools (including `.db` SQLite catalogs, `.parquet`/`.arrow` exports, and emitted `.cs`/`.rs`/`.go` bridge bindings) is not considered a derivative work of UTSS and may be licensed under any terms chosen by the user."*



#### B. Third-Party Introspection & Docstring Harvesting

* **API Signatures & Types:** Harvesting structural metadata (function names, parameter types, arity, AST coordinates) from installed libraries (like `datasets` or `matplotlib`) is standard compiler/bindgen behavior (analogous to `bindgen`, `SWIG`, or TypeScript `.d.ts` generators) and does not trigger copyleft inheritance from the introspected package.


* **Docstrings & Vector Stores:** Because your enrichment pipeline extracts raw docstrings (`raw_docstring`) into SQLite and vector stores, remember that **verbatim docstrings retain the copyright/license of their upstream library** (e.g., Apache-2.0 for Hugging Face `datasets`, PSF/BSD for Python/Matplotlib).


* **Best Practice:** If you distribute pre-built `.db` catalogs or public vector stores containing raw docstrings, include a `THIRD_PARTY_NOTICES.md` listing the upstream packages harvested. If you distribute only **LLM-synthesized normalized summaries** (`normalized_intent_summary`) and structural metadata, those are transformative representations rather than verbatim copies.





#### C. Bundled Dependencies in the Analysis Workbench

* **Frontend (`React_UI`):** Bundles `monaco-editor` (MIT) and React (MIT), both fully compatible with Apache-2.0, MIT, or AGPL-3.0.


* **Backend & ML (`server/`):** Uses `pandas`, `matplotlib`, `duckdb`, and `sqlite3` (all BSD/MIT/Public Domain). Avoid adding GPL-licensed Python libraries (such as `PyQt` or strict GPL C-extensions) to your core workbench dependencies if you intend to keep the core repository under Apache-2.0/MIT.

### 3. Monorepo vs. Multi-Repo Checklist

* **If using a Monorepo (`utss/`):** Put `LICENSE`, `NOTICE`, `THIRD_PARTY_NOTICES.md`, and `CONTRIBUTING.md` at the repository root. Every sub-directory (`harvesters/python`, `harvesters/rust`, `workbench`, `schemas`) inherits them automatically.
* **If using 7 Separate Repositories (`utss-python`, `utss-csharp`, ..., `utss-workbench`):** Copy the exact same `LICENSE` (with the Output Exception) and `NOTICE` into the root of all 7 repositories, and add `"license": "Apache-2.0"` to each sub-project's manifest (`pyproject.toml`, `Cargo.toml`, `package.json`, `.csproj`).






**MIT is an equally valid choice—and slightly simpler for solo or small-team open-source projects—provided you still include the Generated Output Exception.**

For community adoption, developers treat **MIT** and **Apache-2.0** as virtually interchangeable: both are permissive, business-friendly, and compatible with every open-source and proprietary license. However, there are four specific differences that determine which one fits UTSS better:

---

### MIT vs. Apache-2.0 for UTSS

| Factor | MIT License | Apache-2.0 License | Winner for UTSS |
| --- | --- | --- | --- |
| **Simplicity & Friction** | **~170 words.** Easy for anyone to read in 30 seconds; zero `NOTICE` file overhead. | **~1,600 words.** Requires downstream redistributors to preserve a `NOTICE` file and state file modifications. | **MIT** |
| **Patent Protection** | **Implicit only.** Does not include an explicit patent license or patent-retaliation clause. | **Explicit patent grant.** Protects users and contributors against patent lawsuits over compiler/transpiler techniques. | **Apache-2.0** |
| **Ecosystem Alignment** | Standard for **Node/TypeScript**, **Go** (BSD/MIT), and many **Python** tools. | Standard for **Rust** (`MIT OR Apache-2.0`), **.NET/C#** (MIT/Apache), **LLVM**, and **PyTorch**. | **Tie** |
| **Generated Code Safety** | Needs an explicit **Generated Output Exception** so emitted `.db` and `.g.cs` files aren't encumbered. | Needs the same **Generated Output Exception** (plus relieves users of `NOTICE` propagation on emitted files). | **MIT** *(simpler notice rules)* |

---

### Why MIT Might Actually Be Better for Your Workflow

1. **Zero `NOTICE` Propagation on Emitted Bindings:**
Under Apache-2.0, if `utss_csharp_bindgen.py` injects runtime helper boilerplate (`UtssRuntime.g.cs`) into a user's C# project, strict Apache-2.0 compliance technically requires the user to carry your `NOTICE` file when distributing their compiled app—unless your Output Exception explicitly waives it. With **MIT**, there is no `NOTICE` requirement at all; a simple copyright header suffices.


2. **Faster Contributor Onboarding:**
For a community-driven polyglot project with 7 components (6 harvesters + 1 workbench), MIT removes boilerplate across `pyproject.toml`, `Cargo.toml`, `package.json`, `go.mod`, and `.csproj` manifests.


3. **Standard Rust/Python Dual-Licensing Compatibility:**
If you want maximum alignment with the Rust ecosystem (`utss-rust`), the standard Rust convention is **`MIT OR Apache-2.0`**, while using plain **`MIT`** across Python, C#, Go, C++, TypeScript, and the Workbench.
